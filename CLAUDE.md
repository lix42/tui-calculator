# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TUI calculator built with Rust (edition 2024) and Ratatui 0.30 / Crossterm 0.29. Expression-based input (e.g. `78-65*5`) with a button grid UI similar to macOS Calculator.

## Commands

- `cargo run` — run the app (the root package is the native binary)
- `cargo build` — build
- `cargo test --workspace` — run all tests (plain `cargo test` at the root runs only the native binary's tests, not the core's)
- `cargo test --workspace <test_name>` — run a single test
- `cargo clippy --workspace --all-targets` — lint
- `cargo fmt --all` — format
- `cargo build -p calculator-core --target wasm32-unknown-unknown` — check the core still builds for the web
- `cd crates/web && trunk serve` — run the browser build locally (needs `trunk` and the `wasm32-unknown-unknown` target)
- `cd crates/web && trunk build --release --cargo-profile wasm-release --public-url ./` — the deployed build (what `.github/workflows/deploy-web.yml` runs on every push to `main`, publishing the one `dist/` to GitHub Pages and, via `crates/web/wrangler.jsonc`, to Cloudflare Workers Static Assets, served at the Custom Domains `calc.xuli.dev` and `calc.lix42.com` (declared as `routes` in `wrangler.jsonc`; `workers_dev` is off). Stop any running `trunk serve` first: both write `dist/`. `--public-url ./` keeps asset URLs relative, so one `dist/` works under Pages' `/tui-calculator/` subpath and at a host root.

## Architecture

Cargo workspace (`web-core-split`). The **root package** (`tui-calculator`, `src/main.rs`) is the native binary: crossterm, arboard, and the event loop. **`crates/core`** (`calculator-core`, lib) holds every other module and has no crossterm/arboard dependency, so the web build can share it. Its `ratatui` has `default-features = false` (+ `palette`); the defaults include the crossterm backend, which doesn't build for wasm. Deps are per *package*, which is why this is a workspace and not one target-gated package. `main.rs` imports the modules as `calculator_core::{action, app, input, ui, ui_state}`. **Test-support gotcha:** two read-only `UiState` getters (`layout_index`, `override_layout`) that the native tests assert on are gated `#[cfg(any(test, feature = "test-support"))]`, because another crate's tests can't see `cfg(test)` items. The root crate turns `test-support` on only through its **dev**-dependency on the core, so the getters stay out of the API the web crate sees. The other test-only getters (`focus`, `fever_score`) are plain `cfg(test)`: since `web-msg`, only core tests use them.

**`crates/web`** (`calculator-web`, bin, `web-entry`) is the browser entry point: Ratzilla's `DomBackend` + the core, built with Trunk (`crates/web/index.html`). It's a workspace member, so `cargo build/test --workspace` compile it natively too (ratzilla and web-sys build on any target; the tests cover its pure helpers). Like `main.rs` it owns only translation and platform effects, and **it does not use Ratzilla's `on_key_event`/`on_mouse_event`**: those attach to DomBackend's grid `<div>`, which is replaced on every window resize, so they die after the first one. Instead: a `document` capture-phase `keydown` listener, `document` `pointerdown`/`pointerup` listeners (pointer, not mouse, events: iOS Safari doesn't turn a tap into `mousedown` on a non-clickable element), and a `document` `paste` listener (`clipboardData` → core `input::paste`, no permission prompt; Cmd/Ctrl-V can't double up as a `v` key because those chords are left to the browser, whose default is what fires `paste`), `forget()`-ed so they live for the page's lifetime. Keys: Cmd *and* Ctrl chords return early, untouched (they're the browser's shortcuts on macOS and Windows/Linux respectively; Cmd-C would otherwise arrive as a bare `c` and clear); `to_key` turns `KeyboardEvent.key` into a core `Key`; `preventDefault` runs for exactly the keys `key_to_msg` handles (plus `'`, Firefox quick-find), so there's no separate list of keys to suppress. `Msg::Quit` is dropped *before* `preventDefault`. `Msg::Copy` → `navigator.clipboard.writeText`, status set when the promise settles. Held keys repeat, as natively (don't filter `KeyboardEvent.repeat`). Clicks and taps: buttons fire on `pointerdown`; the copy affordance fires on whichever edge `copies_on` picks (`pointerdown` for a mouse, `pointerup` for touch/pen, because only those grant the user gesture `writeText` needs). `cell_at` maps `clientX/Y` through `#grid`'s rect, with the cell counts read from the **DOM** (`<pre>` rows × spans), not `frame.area()`: `GridBackend` makes the two agree, but between a resize and the next frame they briefly differ. `#grid { width: fit-content }` in `index.html` makes rect ÷ count the cell size. **`GridBackend`** (`grid_backend.rs`) wraps `DomBackend` to fix two Ratzilla 0.3.1 bugs: its `size()` uses the physical *screen* on mobile (a frame taller than the DOM grid, so the first draw panics on iPhone), so ours returns the grid size measured exactly as Ratzilla measures it (`measure_grid` mirrors its private code; recheck on a Ratzilla upgrade), measured in `new()` alongside Ratzilla's own and cached until a `resize` — **but only a `resize` after the first draw**: before it, Ratzilla's grid isn't in the document and it doesn't re-measure, so re-measuring ours would reopen the panic; and each `resize` rebuilds the DOM grid blank while ratatui only sends a diff unless the size changed, so its `resize` listener also raises `take_resized`, which the frame loop answers with `Terminal::clear` (resetting ratatui's back buffer, so the draw sends every cell). **The frame loop is ours, not `draw_web`:** `run_frames` in `main.rs` is Ratzilla's `requestAnimationFrame` loop plus that clear, and it logs a failed draw instead of `draw_web`'s `unwrap` panic. `GridBackend::size` never errors (it falls back to Ratzilla's default sizes). Pointer handlers ignore non-primary pointers, so a pinch's second finger can't press a key. **Color gotcha:** DomBackend renders `Color::Reset` as hard-coded white, for a `REVERSED` cell's background too (white-on-white stage-1 press flash, unreadable Light theme). So after `ui::draw`, `resolve_default_colors` replaces every `Reset` fg/bg with the theme's own default (`default_colors`): the web entry plays the terminal and picks its default colors, whose foregrounds match `RESTING_BORDER_L_*` in `ui.rs` so the ripple anchor holds exactly. `paint_body` keeps `<body>`'s background in step with the theme. The theme starts Dark, like native; it is deliberately *not* seeded from `prefers-color-scheme` (Lix's call, 2026-10-08). `auto_select` runs from the `run_frames` closure whenever `frame.area()` changes, including the first frame.

Modules (`src/main.rs`, the rest under `crates/core/src/`):

- **`main.rs`** — terminal setup/teardown, the event loop, and everything genuinely *native*. Keys go through `to_key` (the only crossterm-shaped key code in the program: crossterm `KeyEvent` → core `Key`, dropping Shift because it's already baked into the char) and then the core's `key_to_msg` → `apply_msg`. `Msg::Copy` is intercepted here (`do_copy` → `arboard`), because writing the clipboard is platform code. Also native-only: the `Press`-only filter (Windows reports releases; held-key repeats still arrive as `Press`, since we never opt into `REPORT_EVENT_TYPES`, so holding ⌫ deletes repeatedly), mouse (left-click → `ui.copy_hit` or `ui.button_at` → `ui.button_label` → `activate`), `Event::Resize` → `ui.auto_select`, and `Event::Paste` → the core's `input::paste` (status clear + `App::apply_str`, shared with the web `paste` listener). Paste bypasses `activate` entirely, so it neither climbs fever nor fires the reading grace: paste is one logical edit, and fever is tied to *typing* pace, not input volume. The app launches on the default 5×4 standard pad; auto-selection only adapts the pad on `Event::Resize` (it does *not* seed from the initial `terminal.size()`, so a tiny launch terminal shows the standard pad until the first resize). **Gotcha:** bracketed paste must be enabled in `setup_terminal` (`EnableBracketedPaste`) or `Event::Paste` never fires.
- **`input.rs`** — the backend-neutral input layer (`web-msg`), shared by native and web, so the key rules have one definition and each backend owns only the translation. `Key { code: KeyCode, ctrl, alt }` with the core's own small `KeyCode` (`Other` for anything unused). No `meta`: the web build drops Cmd chords before building a `Key`. `Msg` spans all three subsystems: `Apply(Action)`, `MoveFocus(Dir)`, `ActivateFocused`, `Enter`/`LeaveQuickMode`, `CycleLayout`, `ResumeAuto`, `ToggleTheme`, `Copy`, `Quit`. Pad-switch, theme, quick-mode and copy are `Msg`s, not `Action`s: they change no calculator state, so they stay out of `App::apply`'s pure total match. **`key_to_msg(key, quick_mode)`**: order is the whole job, and each rule is a test. (1) Ctrl-C quits, ahead of the bare `c`, which clears. (2) Quick-mode runs *before* navigation because it reassigns `hjkl`. In-mode, `Esc` leaves the mode whatever the modifiers. With no Ctrl/Alt, a `quick_map` char applies its button (through `from_label`) and an unmapped nav *letter* (`h`) returns `None` (inert), while arrows fall through and still navigate. Ctrl/Alt chords fall through, so Ctrl-U never types `4`. (3) Navigation (`focus_dir`) only with no Ctrl/Alt, so Ctrl-H isn't "move left". (4) Commands (`q`, Tab, `a`, `t`, `y`, `i`, Space) are *not* modifier-gated, then `key_to_action`. **`Esc` is not a quit key** (`q` / Ctrl-C only): it means "leave quick-mode", so the vim reflex of double-tapping it can't discard an expression. There is **no** `r`/`R` toggle any more: fever stage drives mono-vs-rainbow. `apply_msg` is total over `Msg`. `Copy` is a deliberate no-op there (the entry point intercepts it), and `Quit` sets `app.should_quit`, which only the native loop reads. **`activate`** is the shared input funnel (apply → `register_press` → `register_press_fever`). On a *successful* `=` (gated on `app.copy_text().is_some()`, so a syntax error can't claim a success) it also fires the hue drift *and* `register_grace` (2.5 s fever-decay pause). Those two must stay *after* `register_press`, which clears the previous trigger's effects. **`paste(app, ui, text)`** is the shared paste path for native bracketed paste and the web `paste` event: clear status + `App::apply_str`, deliberately *not* `activate` (no fever, flash or grace). `key_to_action` (the keyboard→`Action` map) and `focus_dir` (HJKL/arrows → `Dir`) live here too.
- **`action.rs`** — the typed input boundary. An `Action` enum plus a validated `Digit` newtype (private field, fallible `Digit::new`, so an out-of-range digit is unrepresentable). `from_key` (keyboard ASCII) and `from_label` (button-grid glyphs) resolve raw input into an `Action` *before* it reaches `App`, so illegal input is rejected at the edge instead of mishandled downstream. Also owns `QUICK_MAP`, the quick-input table: a `const &[(char, &str)]` read in *both* directions (`quick_map` / `quick_key`) so routing and the on-screen tips can't drift. It maps to *labels*, not `Action`s, so callers resolve through `from_label`. A `const` slice rather than a `HashMap` because it then lives in rodata with no `LazyLock` or allocation — and at 13 entries a linear scan beats hashing. Pure domain logic — no crossterm dependency.
- **`app.rs`** — `App` holds the calculator state (`expr` tokens, in-progress `current` number, `mode`) and the logic. `App::apply(Action)` is the single input entry point: a total match over the enum, no catch-all. `App::apply_str(&str)` ingests a pasted string, routing each char through `Action::from_label` (the display-glyph boundary, so pasted `×`/`÷` round-trip; unmapped chars skipped) into `apply`.
- **`layout.rs`** — the button layout as *data*, not compiled-in dimensions. A `Keypad` is a lattice of equal cells plus `Button`s that each own a rectangular region (`row/col/row_span/col_span`), so a button can span cells (a wide `0`, a tall `=`). Pads are authored as an occupancy grid of label tokens (a token repeated across adjacent cells *is* a span) and `compile`d at startup, which **validates** the invariants (rectangular grid; each token fills its bounding box — no ragged/disjoint spans) and builds the `cell → button index` occupancy map. Panics on a malformed pad (static data → a programming error). Ships three shape-distinct pads — `Keypad::standard` (5×4, all `1×1`), `Keypad::tall` (7×3 tall-narrow, wide `=` span), `Keypad::wide` (3×7 wide-short, tall `=` span); each carries a `default_focus` resolved from a label at `compile` time (a missing label panics). Exposes a `Dir` enum (Up/Down/Left/Right) and `Keypad::step(row, col, dir)`: the pure one-cell lattice step (a *total* match over `Dir`, no catch-all), returning `None` at the edge — **not** a clamp, since the focus walk loops on it and a clamped edge step would spin. `Keypad::button_distance(a, b)` is the ripple's metric: Manhattan distance measured **rect-to-rect, not anchor-to-anchor**, so a spanning button is equidistant from its neighbours along its whole side instead of radiating from its top-left corner — and it degenerates to plain cell distance for a `1×1` key, so there is no spanning special case. Also owns the cell-geometry constants `CELL_W`/`CELL_H`/`DISPLAY_H` (single source of truth for both the renderer and the fit heuristic) and `Keypad::fit_score(w, h)`: a totally-ordered shape-fit score (a pad that overflows the terminal ranks below every fitting pad; among fitting pads, closest aspect ratio wins). The ratio distance stays in integers via `|need_h*w - h*need_w|`, but that product is the true distance scaled by `need_w*w` — `w` is common to all pads and cancels, while **`need_w` must be divided back out** or each pad is penalised in proportion to its own width, biasing selection toward narrow pads; a `SCALE` factor preserves resolution through the integer division and the arithmetic runs in `i64`. Pure — no ratatui/crossterm dependency.
- **`ui_state.rs`** — `UiState`: a `Vec<Keypad>` registry + active index (all reads funnel through `keypad()`, so multiplying pads didn't re-open the model), button-grid focus (a lattice `(row, col)`), the transient visual **effects** in flight, the per-button screen rects used for mouse hit-testing, and the copy affordance's rect + transient status message. **The press flash is one `EffectKind`, not a special case:** `effects: Vec<Effect>` holds `Effect { kind, started }`, where `EffectKind` is `Press { cell } | Ripple { cell } | Drift` and each variant carries **its own** origin payload (a shared `origin` field would need a meaningless "no origin" case for the global `Drift`). `duration()` is *derived* from the kind, never stored per-effect, so it can't disagree with the constant. `progress()` hands the renderer a normalized `0.0..=1.0` phase and never an `Instant` — that's what makes every animation curve a pure function testable without a clock or a `sleep`. Insertion is **latest-wins**: `start_effects` clears then inserts one trigger's worth (a press starts `Press` *and* `Ripple`), so the "ripples compose" stretch is a change to that one policy rather than to the shape of the state — which is why `effects` is a `Vec` when only one trigger's effects are ever live. `register_drift` is the exception that **appends**, and so must be called *after* `register_press` (which does the clearing) or it's discarded instantly. `set_layout` drops only *cell-anchored* effects (`kind.cell().is_some()`) since their cell may not exist on the new pad; `Drift` is global and rides through. Separately, `animation_start` + `breath_phase()` are a free-running clock for the always-on display breath — it has no trigger and never expires, so modelling it as an `Effect` would mean re-inserting it forever. `button_at` returns a *button index*, hit-testing each button's whole union rect (so a click anywhere on a spanning button — internal seams included — hits it). Focus/flash resolve to a button through the keypad's occupancy map (`is_button_focused` / `is_button_pressed`). Grid navigation steps one *button* per key: `move_focus(Dir)` delegates to the free `next_button_cell`, which walks `Keypad::step` skipping every cell the current button owns, so crossing a span (wide `0`, tall `=`) costs one press. **Within a pad, focus may rest on a non-anchor cell of a span** (it stays on the cell it entered through, which makes the move reversible) — contrast `resolve_focus`, which snaps to the anchor on a pad *switch*. Nav keys map to a `Dir` via `focus_dir` in `main.rs` (the single keyboard→direction boundary). `set_layout`/`cycle_layout` switch the active pad and fix up per-pad state via the free `resolve_focus` (preserve the old cell if in-bounds — snapped to its button's anchor — else the pad's `default_focus`), dropping the stale flash and resizing the hit-test rects. Pad selection is auto-vs-pinned: `auto_select(w, h)` picks the best-fit pad (`select_for` → `Keypad::fit_score`, strict-`>` scan so ties resolve to standard) and switches only when the index actually changes (so a resize that doesn't cross a shape boundary preserves focus/flash); `cycle_layout` (Tab) sets `override_layout = Some(i)` to pin a pad against resizes, and `resume_auto` (`a`) clears it and re-picks for the cached `term_size`. Deliberately separate from `App` (rendering/input-routing vs. calculator logic); `focus` is private, mutated only through bounds-safe methods. Also holds the presentation-only `Theme` (Dark|Light, default Dark, toggled by `t`), and the **fever** state: `fever_score: f64` on `0..=FEVER_MAX` (= 4.0 — **one unit per stage**, not a 0..1 progress bar across four bands), cached `fever_stage: FeverStage` (`One`|`Two`|`Three`|`Four`), `fever_last_tick: Instant` for lazy decay, and `reading_grace_until: Option<Instant>` for the post-`=` pause. `color_mode()` is **derived** (`Rainbow` iff `stage == Four`, else `Mono`) — there is no stored `ColorMode` field and no `toggle_color_mode` method. The score climbs by `FEVER_CLIMB` (0.15) on each `register_press_fever` and decays at `FEVER_DECAY` (0.05/s) continuously, snapped to stages at `1.0/2.0/3.0` with `±FEVER_HYSTERESIS` (0.08) deadband around each — "+0.15 per press on a 0..4 scale" is 15 % of a stage per press, so a burst still *feels* like climbing. The pure helpers `score_after_decay` / `decayed_with_grace` / `next_stage` are unit-tested without a clock. `tick()` applies outstanding decay before every draw; `apply_decay` is private so a test can't forge a time delta (grace-boundary tests pin `reading_grace_until` to `fever_last_tick + FEVER_GRACE` directly). `fever_fill_fraction()` is the renderer-facing accessor: it returns the **sub-stage progress** on `0..=1`, i.e. `(score − lower_threshold_of_current_stage).clamp(0, 1)`, not an overall `score / FEVER_MAX` fraction. Each stage drives the meter 0 → 100 % in its own color, with the previous stage's layer visible behind — a reader comparing this method to its old overall-normalising shape must notice the geometry change in `draw_fever_meter` to match. The `0..=FEVER_MAX` representation is otherwise invisible outside `ui_state.rs`. `FeverStage::colored_highlights`/`animated`/`rainbow` are the gates the renderer reads — press flash is **not** gated on `animated` (it's input confirmation, not decoration). A separate `fever_meter_hue_phase()` is a free-running `0..1` clock for the stage-Four meter's slow 20 s hue rotation, parallel to `breath_phase()`. `Theme` affects **both** color modes (rainbow digit hues *and* the colored stage-Two mono highlight accents). Also `quick_mode: bool` — a setter, not a toggle, because the triggers are one-way and live in different states (`i` only enters; in-mode `i` types `5`, and only `Esc` leaves).
- **`eval.rs`** — recursive-descent evaluator over `Token`s with operator precedence, parentheses, and unary minus.
- **`ui.rs`** — Ratatui rendering: the display box (reads `&App`) and the button grid (reads `&mut UiState`). `draw_buttons` splits the area into a runtime-sized coordinate lattice (`Layout::split` → `Rc<[Rect]>`, no const generics) and draws each button once over the bounding box of the cells it spans; the panel is sized from the active keypad's dims and the `CELL_W`/`CELL_H`/`DISPLAY_H` constants (imported from `layout.rs`, where the fit heuristic also reads them), not magic numbers. **Color/rainbow rendering lives here too.** `glyph_color` is the single source of truth for both the button grid and the display — per-glyph hues built in **HSLuv** via ratatui's `palette` feature (enabled in `Cargo.toml`) so digit hues read evenly bright (digits `0`–`9` on a 36° hue grid, operators/parens hand-picked off-grid; `=`/`C`/`⌫`/`.` stay neutral). `filled_style` and `outline_style` are the two highlight shapes; `knockout` (glyph painted over a fill) and `loud` (the loudest fill) are deliberately **opposite ends of the scale**, so a `loud`-filled chip never knocks out same-on-same — the light-theme white-on-white trap. Mono focus/press derive from the palette (no static accent color): colored keys are outline-on-focus / fill-on-press, while neutral keys use `loud` with the shapes **swapped** (fill-on-focus / outline-on-press, since a faint outline reads too close to the resting cell); rainbow fills on both states. The display is colored per-character by `rainbow_spans` (borrowed slices; `char_indices` keeps multibyte `×`/`÷` whole), while mono keeps the borrow-only `Line::from(&str)` path — both selected by `styled_line`. `draw_button` takes a `ButtonView` (label / focused / pressed / tip / ripple) plus the fever stage — clippy's `too_many_arguments` fires at 8, so per-button state must be grouped to add a field. **Fever gates:** `draw_button` dispatches on `stage.colored_highlights()` → `button_style` (stages 2-4, mono/rainbow split inside) vs. `plain_style` (stage 1, color-free: `BorderType::Thick` on focus, `Modifier::REVERSED` on press, no explicit fg/bg so the terminal's own default drives the flash and the Light theme is covered for free). The press flash is **not** gated — it rides as a `pressed: bool` through both styles, since it's input confirmation. Quick-input tips ride in each button's **top border** via `Block::title`: after `Padding::symmetric(2, 1)` the interior is one column wide, so there is no room beside the glyph. They draw only while quick-mode is on, doubling as the mode indicator. **Shortcut help line:** `draw` adds a third `HELP_H` row under the grid while `ui.show_help()` (on by default; the web entry turns it off when `touch_first()`, the `(hover: none) and (pointer: coarse)` media query, holds). `help_items(quick_mode, pinned)` is the priority-ordered list (no `y`: the `[y Copy]` hint covers it) and `help_pages` greedily packs whole items into panel-width pages; `draw_help` shows page `ui.help_tick() % len`, a free-running clock flipping every `HELP_PAGE_PERIOD`. A page *flip*, not a sliding ticker, so stage 1 stays still. The row is reserved by `UiState::select_for` (subtracted from the height the pads compete for), not by `Keypad::fit_score`, since it's a per-host setting. `ui.rs` tests render through `ratatui::backend::TestBackend` at `28×30` (the standard pad's exact panel size, help row included) and assert on buffer cells (fg equivalence treats `None` and `Some(Color::Reset)` as "default"), so layout claims are verified rather than argued in prose. **Animation lives here too** (the model is in `ui_state.rs`; the *curves* are here, pure and clock-free). A `Palette { theme, drift }` replaces the bare `Theme` in every hue-building signature, so a palette-wide modulation doesn't widen them all again; `frame_palette` resolves it **once per frame** so the display and grid can't disagree, and gates the drift on `stage.rainbow()` at the call site; `palette_for` separately refuses to drift under `ColorMode::Mono` as part of its own contract (that half is a general property of `palette_for`, not a backstop for the stage gate — the two expressions are currently tautologically equivalent, since `color_mode()` is derived from `stage == Four`, so they can't disagree). Three effects: the **ripple** (`ripple_intensity(distance, phase)` — a per-ring delayed flash; `apply_ripple` lights the *border* and yields entirely on a focused/pressed key, since the pressed key sits at distance 0 and would otherwise overwrite its own `loud` chip; **gated on `stage.animated()`** at the `draw_buttons` level — stages 1-2 skip reading the ripple from `effects` so `view.ripple` stays `0.0` and `apply_ripple` short-circuits), the **hue drift** on a successful `=` (`drift_offset` is a half-sine, zero at *both* ends so the palette leaves and returns continuously; rainbow-only, so stages 1-3 can't see it), and the **display breath** (`breath_color`, a full sine so the loop point is invisible; gated on `stage.animated()` — stages 1-2 render the display border in the terminal default). **Fever meter visual:** `draw_fever_meter` runs *after* the display block renders, overlaying the bottom border with a **per-stage** geometry: each stage drives the fill 0 → 100 % of width in its own color, then the next stage overlays from the right while the previous stage's color stays on the left as a base layer. Three regions, drawn right-to-left: (1) the **current fill** (`round(fever_fill_fraction * area.width)` cells, where `fever_fill_fraction` is per-stage, not overall) in the current stage's color, (2) a single-cell `<` **marker** at the layer boundary when both regions have width (so the eye can find the fill head between two close grays — the three stage colors are deliberately similar), and (3) the **base layer** on the left in the previous stage's color (stages 2-4) or *erased with a space* (stage 1, where "below" is nothing — the display's bottom edge is literally not drawn until the meter has climbed into it). Color helpers: `fever_meter_color` (current) and `base_meter_color` (previous, `None` for stage 1) both delegate to `stage_meter_color`, which maps stages 1-3 to a three-tier `meter_gray` (dim / medium / bright, HSLuv saturation 0, moving away from background per theme — same convention as `loud`/`knockout`/ripple/breath) and stage 4 to `stage_four_meter(fever_meter_hue_phase, theme)` (drifting hue). Grays, not hues, for stages 1-3 so stage 4's drift is the one place a color appears — the ladder *earns* color. **Invariant:** `RIPPLE_RING_DELAY * max_distance + RIPPLE_RING_FADE <= 1.0`, or the outermost ring is still lit when `phase` clamps at `1.0` and pops — note this is *not* fixable by lengthening `RIPPLE_DURATION`, since `phase` is normalized; guarded by `ripple_completes_before_expiring_on_every_pad`, which measures the real pads. **Only the drift is rainbow-only** (mono has no hues to rotate); the ripple and breath ride on **lightness** at zero HSLuv saturation — which *is* a gray — so one code path serves both color modes with no mono branch. **Ripple color gotcha (fixed once, easy to reintroduce):** a resting button's `border_style` is `Style::new()` — *no* `fg` — so it renders in the terminal's **default foreground**, already bright on dark (~L 80). `ripple_lightness` must therefore anchor its ramp at `RESTING_BORDER_L_*`, not at an absolute endpoint: `apply_ripple` stops painting below `RIPPLE_FLOOR` and hands back the *unstyled* base, so any other anchor makes every ring snap at its trailing edge. The peak stops short of `100`/`0` because HSLuv at either extreme is white/black at **any** saturation, which would erase the hue the rainbow ripple carries — the same trap as the light-theme `loud`/`knockout` bug. Saturation ramps with intensity as well, so rainbow is carried by saturation (little lightness headroom above the resting border) and mono by lightness (no hue to grow into).

Input is **expression-based** (digits, `+-*/`, parentheses); keyboard (HJKL/arrows navigate the grid), mouse clicks, and bracketed paste all funnel through the same `Action` boundary.

**`README.md` documents every user-facing key** in two tables. It is easy to forget and has silently rotted before (it described a Copy *button* that never shipped, and missed five keys across four PRs). Any change that adds, removes, or repurposes a key must update it — `docs/` is not the user-facing surface.

Key dependencies: `ratatui` (TUI rendering), `crossterm` (terminal input), `arboard` (system clipboard, `wayland-data-control` feature on for pure-Wayland support — used by `do_copy` in `main.rs`), `web-time` (the `Instant` behind the press flash and copy status in `ui_state.rs`). **`web-time` gotcha:** it must stay a plain `[dependencies]` entry, **not** target-gated to wasm. It's a drop-in that re-exports `std`'s `Instant` on native and only swaps in `performance.now()` on `wasm32` (where `std`'s would *panic*) — and `ui_state.rs` is shared code the native binary compiles too, so gating it on `cfg(target_arch = "wasm32")` breaks the native build with an unresolved `web_time` import. Swapped in ahead of both `rainbow-animation` and the web port so neither carries a clock gap. **Clipboard gotcha:** on Linux the copied text is served by the live `Clipboard` instance, so `copy_to_clipboard` keeps one handle in a process-lifetime `thread_local` (`CLIPBOARD`) rather than building one per copy — a fresh-per-copy handle would let `set_text` report success while the paste silently fails. Even so, on Linux the text may not survive app exit without a clipboard manager (macOS/Windows persist it).

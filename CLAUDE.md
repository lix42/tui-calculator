# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TUI calculator built with Rust (edition 2024) and Ratatui 0.30 / Crossterm 0.29. Expression-based input (e.g. `78-65*5`) with a button grid UI similar to macOS Calculator.

## Commands

- `cargo run` — run the app
- `cargo build` — build
- `cargo test` — run all tests
- `cargo test <test_name>` — run a single test
- `cargo clippy` — lint
- `cargo fmt` — format

## Architecture

Modules under `src/`:

- **`main.rs`** — terminal setup/teardown and the event loop. `handle_event` resolves each key/mouse event to an `Action` (or a focus move) and dispatches it; `key_to_action` is the single keyboard→`Action` map. A left-click resolves to a button index via `ui.button_at`, then to its label via `ui.button_label`. `Event::Paste` feeds the pasted string to `App::apply_str`. Copy-to-clipboard (`y`/`Y` or a click on the display affordance → `do_copy` → `arboard`), manual pad-switching (`Tab` → `ui.cycle_layout`, which *pins* the pad), resume-auto (`a`/`A` → `ui.resume_auto`), rainbow-mode toggle (`r`/`R` → `ui.toggle_color_mode`), palette-theme toggle (`t`/`T` → `ui.toggle_theme`), quick-input mode (`i` → `ui.set_quick_mode(true)`), and shape-based auto-select on resize (`Event::Resize` → `ui.auto_select`) are all routed *here*, not as an `Action`: they're side effects on the UI/result that change no calculator state, so they stay out of `App::apply`'s pure total match and out of `action.rs`. The app launches on the default 5×4 standard pad; auto-selection only adapts the pad on `Event::Resize` (it does *not* seed from the initial `terminal.size()`, so a tiny launch terminal shows the standard pad until the first resize). **Gotcha:** bracketed paste must be enabled in `setup_terminal` (`EnableBracketedPaste`) or `Event::Paste` never fires. **`Esc` is not a quit key** (`q` / `Ctrl-C` only): it means "leave quick-mode", so the vim reflex of double-tapping it can't discard an expression. The quick-mode block sits *before* the nav gate (it reassigns `hjkl`) and must repeat the same `!intersects(CONTROL|ALT)` guard — without it `Ctrl-U` types `4`.
- **`action.rs`** — the typed input boundary. An `Action` enum plus a validated `Digit` newtype (private field, fallible `Digit::new`, so an out-of-range digit is unrepresentable). `from_key` (keyboard ASCII) and `from_label` (button-grid glyphs) resolve raw input into an `Action` *before* it reaches `App`, so illegal input is rejected at the edge instead of mishandled downstream. Also owns `QUICK_MAP`, the quick-input table: a `const &[(char, &str)]` read in *both* directions (`quick_map` / `quick_key`) so routing and the on-screen tips can't drift. It maps to *labels*, not `Action`s, so callers resolve through `from_label`. A `const` slice rather than a `HashMap` because it then lives in rodata with no `LazyLock` or allocation — and at 13 entries a linear scan beats hashing. Pure domain logic — no crossterm dependency.
- **`app.rs`** — `App` holds the calculator state (`expr` tokens, in-progress `current` number, `mode`) and the logic. `App::apply(Action)` is the single input entry point: a total match over the enum, no catch-all. `App::apply_str(&str)` ingests a pasted string, routing each char through `Action::from_label` (the display-glyph boundary, so pasted `×`/`÷` round-trip; unmapped chars skipped) into `apply`.
- **`layout.rs`** — the button layout as *data*, not compiled-in dimensions. A `Keypad` is a lattice of equal cells plus `Button`s that each own a rectangular region (`row/col/row_span/col_span`), so a button can span cells (a wide `0`, a tall `=`). Pads are authored as an occupancy grid of label tokens (a token repeated across adjacent cells *is* a span) and `compile`d at startup, which **validates** the invariants (rectangular grid; each token fills its bounding box — no ragged/disjoint spans) and builds the `cell → button index` occupancy map. Panics on a malformed pad (static data → a programming error). Ships three shape-distinct pads — `Keypad::standard` (5×4, all `1×1`), `Keypad::tall` (7×3 tall-narrow, wide `=` span), `Keypad::wide` (3×7 wide-short, tall `=` span); each carries a `default_focus` resolved from a label at `compile` time (a missing label panics). Exposes a `Dir` enum (Up/Down/Left/Right) and `Keypad::step(row, col, dir)`: the pure one-cell lattice step (a *total* match over `Dir`, no catch-all), returning `None` at the edge — **not** a clamp, since the focus walk loops on it and a clamped edge step would spin. Also owns the cell-geometry constants `CELL_W`/`CELL_H`/`DISPLAY_H` (single source of truth for both the renderer and the fit heuristic) and `Keypad::fit_score(w, h)`: a totally-ordered shape-fit score (a pad that overflows the terminal ranks below every fitting pad; among fitting pads, closest aspect ratio wins). The ratio distance stays in integers via `|need_h*w - h*need_w|`, but that product is the true distance scaled by `need_w*w` — `w` is common to all pads and cancels, while **`need_w` must be divided back out** or each pad is penalised in proportion to its own width, biasing selection toward narrow pads; a `SCALE` factor preserves resolution through the integer division and the arithmetic runs in `i64`. Pure — no ratatui/crossterm dependency.
- **`ui_state.rs`** — `UiState`: a `Vec<Keypad>` registry + active index (all reads funnel through `keypad()`, so multiplying pads didn't re-open the model), button-grid focus (a lattice `(row, col)`), the momentary press flash, the per-button screen rects used for mouse hit-testing, and the copy affordance's rect + transient status message. `button_at` returns a *button index*, hit-testing each button's whole union rect (so a click anywhere on a spanning button — internal seams included — hits it). Focus/flash resolve to a button through the keypad's occupancy map (`is_button_focused` / `is_button_pressed`). Grid navigation steps one *button* per key: `move_focus(Dir)` delegates to the free `next_button_cell`, which walks `Keypad::step` skipping every cell the current button owns, so crossing a span (wide `0`, tall `=`) costs one press. **Within a pad, focus may rest on a non-anchor cell of a span** (it stays on the cell it entered through, which makes the move reversible) — contrast `resolve_focus`, which snaps to the anchor on a pad *switch*. Nav keys map to a `Dir` via `focus_dir` in `main.rs` (the single keyboard→direction boundary). `set_layout`/`cycle_layout` switch the active pad and fix up per-pad state via the free `resolve_focus` (preserve the old cell if in-bounds — snapped to its button's anchor — else the pad's `default_focus`), dropping the stale flash and resizing the hit-test rects. Pad selection is auto-vs-pinned: `auto_select(w, h)` picks the best-fit pad (`select_for` → `Keypad::fit_score`, strict-`>` scan so ties resolve to standard) and switches only when the index actually changes (so a resize that doesn't cross a shape boundary preserves focus/flash); `cycle_layout` (Tab) sets `override_layout = Some(i)` to pin a pad against resizes, and `resume_auto` (`a`) clears it and re-picks for the cached `term_size`. Deliberately separate from `App` (rendering/input-routing vs. calculator logic); `focus` is private, mutated only through bounds-safe methods. Also holds the presentation-only `ColorMode` (Mono|Rainbow, default **Rainbow**) and `Theme` (Dark|Light, default Dark), toggled by the `r`/`t` keys and read by the renderer — on `UiState` not `App` because color changes no calculator state. `Theme` affects **both** modes (rainbow digit hues *and* mono highlight accents), not just rainbow. Also `quick_mode: bool` — a setter, not a toggle, because the triggers are one-way and live in different states (`i` only enters; in-mode `i` types `5`, and only `Esc` leaves).
- **`eval.rs`** — recursive-descent evaluator over `Token`s with operator precedence, parentheses, and unary minus.
- **`ui.rs`** — Ratatui rendering: the display box (reads `&App`) and the button grid (reads `&mut UiState`). `draw_buttons` splits the area into a runtime-sized coordinate lattice (`Layout::split` → `Rc<[Rect]>`, no const generics) and draws each button once over the bounding box of the cells it spans; the panel is sized from the active keypad's dims and the `CELL_W`/`CELL_H`/`DISPLAY_H` constants (imported from `layout.rs`, where the fit heuristic also reads them), not magic numbers. **Color/rainbow rendering lives here too.** `glyph_color` is the single source of truth for both the button grid and the display — per-glyph hues built in **HSLuv** via ratatui's `palette` feature (enabled in `Cargo.toml`) so digit hues read evenly bright (digits `0`–`9` on a 36° hue grid, operators/parens hand-picked off-grid; `=`/`C`/`⌫`/`.` stay neutral). `filled_style` and `outline_style` are the two highlight shapes; `knockout` (glyph painted over a fill) and `loud` (the loudest fill) are deliberately **opposite ends of the scale**, so a `loud`-filled chip never knocks out same-on-same — the light-theme white-on-white trap. Mono focus/press derive from the palette (no static accent color): colored keys are outline-on-focus / fill-on-press, while neutral keys use `loud` with the shapes **swapped** (fill-on-focus / outline-on-press, since a faint outline reads too close to the resting cell); rainbow fills on both states. The display is colored per-character by `rainbow_spans` (borrowed slices; `char_indices` keeps multibyte `×`/`÷` whole), while mono keeps the borrow-only `Line::from(&str)` path — both selected by `styled_line`. `draw_button` takes a `ButtonView` (label / focused / pressed / tip) rather than loose arguments — clippy's `too_many_arguments` fires at 8, so per-button state must be grouped to add a field. Quick-input tips ride in each button's **top border** via `Block::title`: after `Padding::symmetric(2, 1)` the interior is one column wide, so there is no room beside the glyph. They draw only while quick-mode is on, doubling as the mode indicator. `ui.rs` tests render through `ratatui::backend::TestBackend` at `28×29` (the standard pad's exact panel size) and assert on buffer cells, so layout claims are verified rather than argued in prose.

Input is **expression-based** (digits, `+-*/`, parentheses); keyboard (HJKL/arrows navigate the grid), mouse clicks, and bracketed paste all funnel through the same `Action` boundary.

**`README.md` documents every user-facing key** in two tables. It is easy to forget and has silently rotted before (it described a Copy *button* that never shipped, and missed five keys across four PRs). Any change that adds, removes, or repurposes a key must update it — `docs/` is not the user-facing surface.

Key dependencies: `ratatui` (TUI rendering), `crossterm` (terminal input), `arboard` (system clipboard, `wayland-data-control` feature on for pure-Wayland support — used by `do_copy` in `main.rs`). **Clipboard gotcha:** on Linux the copied text is served by the live `Clipboard` instance, so `copy_to_clipboard` keeps one handle in a process-lifetime `thread_local` (`CLIPBOARD`) rather than building one per copy — a fresh-per-copy handle would let `set_text` report success while the paste silently fails. Even so, on Linux the text may not survive app exit without a clipboard manager (macOS/Windows persist it).
